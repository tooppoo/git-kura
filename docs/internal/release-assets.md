# Release Assets

This document is the authoritative reference for the files that make up a git-kura GitHub Release, their relationships, and how the `release-asset` validate-only step verifies them.

The design rationale and background decisions for the release support script are recorded in the parent issue (#105) and [20260702T050859Z_goreleaser-artifacts-before-release.md](../adr/20260702T050859Z_goreleaser-artifacts-before-release.md). This document describes what the release assets are and how they relate to each other.

## Asset overview

A git-kura GitHub Release for version `v<VERSION>` (e.g. `v0.0.7`) contains the following assets. GoReleaser's `.Version` template variable omits the leading `v` (e.g. `0.0.7`); the naming conventions below use both forms explicitly.

### Platform archive assets

Six platform binary archives built by GoReleaser from the `release-archives` archive ID:

| OS      | Arch  | Filename                                       |
|---------|-------|------------------------------------------------|
| Linux   | amd64 | `git-kura_v<VERSION>_Linux_x86_64.tar.gz`     |
| Linux   | arm64 | `git-kura_v<VERSION>_Linux_arm64.tar.gz`      |
| macOS   | amd64 | `git-kura_v<VERSION>_Darwin_x86_64.tar.gz`    |
| macOS   | arm64 | `git-kura_v<VERSION>_Darwin_arm64.tar.gz`     |
| Windows | amd64 | `git-kura_v<VERSION>_Windows_x86_64.zip`      |
| Windows | arm64 | `git-kura_v<VERSION>_Windows_arm64.zip`       |

These archives each contain the `git-kura` binary, `README.md`, `LICENSE`, and `third_party_licenses/`.

### checksums.txt

`checksums.txt` is generated by GoReleaser's `checksum` configuration with `algorithm: sha256` and `ids: [release-archives]`. It covers all six platform archives listed above.

Each line has the form:
```
<sha256hex>  <filename>
```

`checksums.txt` does **not** cover the tools archive or the tools sidecar manifest. The tools archive checksum is provided by the tools sidecar manifest instead.

### checksums.txt.sigstore.json

`checksums.txt.sigstore.json` is the Sigstore/cosign keyless signature bundle for `checksums.txt`. It is generated by GoReleaser's `signs` configuration with `artifacts: checksum`.

This file confirms the provenance of `checksums.txt`. Cryptographic signature verification is out of scope for the `release-asset` validate step; only existence in GoReleaser's artifacts output and on disk is confirmed.

### SBOM assets

GoReleaser calls Syft for each platform archive (`artifacts: archive` in `.goreleaser.yml`). Each archive receives a corresponding SBOM file named `<archive_filename>.sbom.json`:

| Archive                                        | SBOM                                                   |
|------------------------------------------------|--------------------------------------------------------|
| `git-kura_v<VERSION>_Linux_x86_64.tar.gz`     | `git-kura_v<VERSION>_Linux_x86_64.tar.gz.sbom.json`   |
| `git-kura_v<VERSION>_Linux_arm64.tar.gz`      | `git-kura_v<VERSION>_Linux_arm64.tar.gz.sbom.json`    |
| `git-kura_v<VERSION>_Darwin_x86_64.tar.gz`    | `git-kura_v<VERSION>_Darwin_x86_64.tar.gz.sbom.json`  |
| `git-kura_v<VERSION>_Darwin_arm64.tar.gz`     | `git-kura_v<VERSION>_Darwin_arm64.tar.gz.sbom.json`   |
| `git-kura_v<VERSION>_Windows_x86_64.zip`      | `git-kura_v<VERSION>_Windows_x86_64.zip.sbom.json`    |
| `git-kura_v<VERSION>_Windows_arm64.zip`       | `git-kura_v<VERSION>_Windows_arm64.zip.sbom.json`     |

SBOM content schema validation and archive-content consistency checks are out of scope for the `release-asset` validate step. The step confirms each expected SBOM exists in GoReleaser's artifacts output and on disk, and that each SBOM file parses as JSON.

### Tools archive and sidecar manifest

Two extra files are attached to each release via GoReleaser's `release.extra_files` configuration:

| Artifact          | Naming convention                        |
|-------------------|------------------------------------------|
| Tools archive     | `git-kura-tools_<goreleaser_version>.tar.gz` |
| Sidecar manifest  | `git-kura-tools_<goreleaser_version>.json`   |

where `<goreleaser_version>` is GoReleaser's `.Version` (without `v` prefix), e.g. `0.0.7`.

The sidecar manifest is the authoritative checksum source for the tools archive. `checksums.txt` does **not** cover the tools archive.

#### Sidecar manifest fields

```json
{
  "archiveName": "git-kura-tools_<goreleaser_version>.tar.gz",
  "archiveChecksum": "<sha256-hex>",
  "checksumAlgorithm": "sha256",
  "version": "<goreleaser_version>"
}
```

The `release-asset` validate step reads the local sidecar manifest and verifies that:

- `version` equals the GoReleaser version string (CLI version without `v`).
- `archiveName` equals the expected tools archive filename.
- `archiveChecksum` is a valid 64-character lowercase sha256 hex string.
- `archiveChecksum` matches the sha256 of the local tools archive.
- `checksumAlgorithm` is `sha256`.

See [tools-asset-distribution.md](tools-asset-distribution.md) for the full specification of the tools archive format and how `git kura tools install` uses these fields.

### Package manager Windows archives

The external Scoop bucket repository workflow references the Windows platform archives from the GitHub Release assets after the release workflow uploads them. The Scoop bucket manifest update is not a git-kura release step; it is performed by the `catalog-scoop-bucket` repository's own workflow. The relevant files and their expected filenames are:

| Architecture | Filename                                  |
|--------------|-------------------------------------------|
| amd64        | `git-kura_v<VERSION>_Windows_x86_64.zip` |
| arm64        | `git-kura_v<VERSION>_Windows_arm64.zip`  |

These are the same files as the Windows platform archives. They are also checked separately in the `release-asset` validate result as `package-manager-windows-archive` entries so the release workflow proves both Windows architectures are present before GitHub Release creation.

### Package manager macOS archives

The external Homebrew tap repository workflow references the macOS platform archives from the same GitHub Release. It does not require or publish any Homebrew-only release asset. The relevant files and their expected filenames are:

| Architecture | Filename                                     |
|--------------|----------------------------------------------|
| arm64        | `git-kura_v<VERSION>_Darwin_arm64.tar.gz`   |
| amd64        | `git-kura_v<VERSION>_Darwin_x86_64.tar.gz`  |

These are the same files as the macOS platform archives listed above. For each architecture the external Homebrew tap repository workflow reads the archive URL from the GitHub Release asset list and its sha256 from `checksums.txt`, then writes both into `Formula/git-kura.rb` in the tap repository. Because both the archive URL and its checksum come from the same release, a Homebrew install verifies the exact bytes covered by that release's `checksums.txt`.

## Asset relationships

```
checksums.txt
  └── covers sha256 of all six platform archives
        (does NOT cover tools archive or tools sidecar)

checksums.txt.sigstore.json
  └── Sigstore signature bundle for checksums.txt

git-kura_v<VERSION>_<OS>_<ARCH>.<EXT>  (6 platform archives)
  └── git-kura_v<VERSION>_<OS>_<ARCH>.<EXT>.sbom.json  (SBOM per archive)

git-kura-tools_<goreleaser_version>.tar.gz  (tools archive)
  └── git-kura-tools_<goreleaser_version>.json  (sidecar; provides archiveChecksum)

Windows platform archives (amd64 + arm64)
  └── uploaded to GitHub Release, then referenced by the external Scoop bucket repository workflow

macOS (Darwin) platform archives (arm64 + amd64)
  └── uploaded to GitHub Release, then referenced with checksums.txt sha256 for the external Homebrew tap workflow
```

## Release workflow validation

The release workflow runs GoReleaser with `release --clean --skip=publish`. GoReleaser generates local artifacts under `dist` and exposes `metadata` and `artifacts` JSON outputs.

The `release-asset` validate step treats the GoReleaser `artifacts` output as the source of truth for selecting upload candidates. It excludes local-only artifacts such as `Metadata` and `Binary`, applies an allowlist for platform archives, checksums, signature bundle, SBOMs, tools archive, and tools sidecar manifest, and validates the same selected local files that will be uploaded.

Because the workflow uses `--skip=publish`, GoReleaser does not run the release publisher that would normally add `release.extra_files` to its artifact set. The tools archive and sidecar are generated by the GoReleaser `before` hook under `.tools-dist`, so the validator promotes those two expected files into its upload candidate metadata when they are absent from `artifacts.json`.

On success, the step writes a newline-delimited `files` output for `softprops/action-gh-release`. The workflow uses that exact output as the action's `files` input, with `fail_on_unmatched_files: true` and `overwrite_files: false`.
