# Validate GoReleaser Artifacts Before GitHub Release Creation

- Status: Accepted
- Created: 2026-07-02T05:08:59Z

## Context

The `scripts/release` support code is a maintainer-facing release guard for the main git-kura repository. It is not the package-manager repository update framework; Homebrew tap and Scoop bucket updates are handled by those repositories' own workflows.

git-kura still needs to publish a coherent GitHub Release containing platform archives, `checksums.txt`, `checksums.txt.sigstore.json`, archive SBOMs, a tools archive, and a tools sidecar manifest. These files are consumed by users and by external package-manager workflows, so the release workflow should validate them before they become public Release assets.

One option was to let GoReleaser create a draft GitHub Release, inspect the draft assets, and publish the draft after validation. That creates avoidable dependence on GitHub API visibility and permissions for draft releases. Another option was to inspect already attached Release assets through the GitHub Release asset API, but that validates after upload and depends on GitHub download behavior.

## Decision

GoReleaser must not publish the GitHub Release in the main release workflow.

The release workflow must run GoReleaser with:

```sh
release --clean --skip=publish
```

GoReleaser is responsible for generating local release artifacts and exposing its `metadata` and `artifacts` JSON outputs. The `release-asset` validate step must validate the GoReleaser outputs and the corresponding local files under `dist`.

The `artifacts` output is the source of truth for selecting upload candidates. The validator must exclude local-only artifacts, including at least `Metadata` and `Binary`, and must include only allowlisted release files: platform archives from the `release-archives` archive ID, `checksums.txt`, `checksums.txt.sigstore.json`, archive SBOMs, the tools archive, and the tools sidecar manifest.

GoReleaser adds `release.extra_files` to its artifact set inside the release publisher, which is skipped by `--skip=publish`. Therefore, the tools archive and tools sidecar manifest generated by the GoReleaser `before` hook are the only files the validator may promote from the configured tools output directory when they are absent from `artifacts.json`.

On validation success, the validator must emit the exact newline-delimited file list that `softprops/action-gh-release` receives through its `files` input. GitHub Release creation and asset upload are delegated to `softprops/action-gh-release`, with `generate_release_notes: true`, `fail_on_unmatched_files: true`, and `overwrite_files: false`.

The workflow must not specify `previous_tag`; GitHub's release note generation should choose the previous tag automatically.

## Alternatives Considered

### GoReleaser Publishes the GitHub Release

This keeps publication in one tool, but it does not leave a clear validation gate between artifact generation and GitHub Release creation. It was rejected because git-kura needs to verify generated artifacts before upload.

### GoReleaser Creates a Draft Release

This would allow validation before publication, but it requires identifying and inspecting draft release assets through GitHub APIs. It was rejected because draft release visibility and permissions add operational ambiguity.

### Validate Already Uploaded GitHub Release Assets

This validates the public assets directly, but it happens after upload and depends on GitHub Release asset API behavior. It was rejected as the primary release guard because the workflow should stop before release creation when validation fails.

## Consequences

### Positive Consequences

- The release workflow has a deterministic validation gate before GitHub Release creation.
- The validated local files and uploaded file list are identical.
- Draft release discovery and GitHub Release asset download validation are out of the release guard's critical path.
- Existing Release assets are not implicitly deleted, overwritten, or repaired by the workflow.

### Negative Consequences

- The workflow trusts GoReleaser's local artifact generation and `artifacts` output as the boundary before upload.
- The validator does not prove that GitHub stores the uploaded bytes exactly as provided; it proves the files selected for upload are coherent before handoff to `softprops/action-gh-release`.
- Existing Release reconciliation remains out of scope.

### Neutral Consequences

- Package-manager repository updates remain outside the main repository release script.
- GitHub-generated release notes remain the release notes source for now.
